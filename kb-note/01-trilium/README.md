## 二、存储方式

**范式:单文件数据库(SQLite)**

```
trilium-data/
├── document.db      # 核心:所有笔记+附件+版本+配置,单 SQLite
├── backup/          # 自动定时备份
└── log/             # 日志
```

| 维度 | 说明 |
| --- | --- |
| 存储形态 | 单个 `document.db` SQLite 文件 |
| 备份 | 复制一个文件即全部备份 |
| 纯文本 | ❌ 二进制,无法 Git diff |
| 迁移 | 导出 MD/OPML(有损) |
| 锁定风险 | 中,依赖导出功能 |
| 版本历史 | 入库(同一 DB) |
| 加密 | 保护模式下整库加密 |
| 十万级体量 | ✅ 数据库索引优化 |

**优点**:备份极简、事务一致性强、大数据量性能好、结构化查询(SQL)。
**缺点**:二进制不可 diff、脱离工具不可直读、单点故障需勤备份。

## 三、链接功能(五款中最强)

**评级:L5 —— 关系作为一等公民**

链接体系两层:

1. **普通链接**:正文内部链接,仅跳转。

2. **关系属性(Relation)—— 核心特色**:
   - 每个笔记可挂属性,分两类:
     - `label`:键值对标量(如 `类型:: 书籍`、`评分:: 5`)
     - `relation`:**指向另一笔记的带名链接** —— 带属性的三元组
   - 结构等价于知识三元组:`(本笔记, 关系名, 目标笔记)`

```
示例:
笔记《狂人日记》
  ├─ label:    类型 = 书籍
  ├─ label:    发布年份 = 1918
  ├─ relation: 作者 ──► 笔记《鲁迅》
  └─ relation: 收录于 ──► 笔记《呐喊》
```

- **关系可查询**:内置搜索语法或 SQL 直接查图("所有作者=鲁迅的作品"、"被 ≥3 篇笔记引用的来源")
- **关系可视化**:Relation Map 按关系类型渲染
- **链接本身带元数据**:关系是数据库记录而非正文文本

**结论**:最接近 Palantir 式本体/知识图谱建模的笔记工具。

## 四、MCP 与 AI 接入

**评级:T1 —— 官方 API + 成熟社区适配**

| 维度 | 说明 |
| --- | --- |
| 官方 MCP | ❌ |
| 自有 API | ✅ ETAPI(REST),覆盖笔记 CRUD、搜索、附件、属性(含 relation) |
| MCP 路径 | 社区适配器(mcp-trilium 等)→ ETAPI → 笔记库 |
| 配置难度 | 中(启动适配器 + 配 token + 注册 AI 客户端) |
| 内置 AI | ❌(JS 脚本可自建 AI 管道) |

**优势场景**:
- **结构化读写**:ETAPI 直接操作 relation 属性,AI 可做知识图谱级检索("列出作者=鲁迅的所有笔记")
- JS 脚本引擎可调 OpenAI/Claude API 批处理笔记、定时自动化

**短板**:无官方 MCP;需保持服务端运行;配置门槛中等。

## 五、便携支持(五款中唯一官方原生全便携)

**评级:官方 Portable 标杆**

| 维度 | 说明 |
| --- | --- |
| 官方便携版 | ✅ **官方提供 Portable 压缩包** |
| 数据位置 | 默认在程序目录 `trilium-data/`(程序与数据天然一体) |
| 系统写入 | ❌ 不写系统盘和注册表 |
| 免安装跨机 | ✅ 解压到 U 盘即用,拔掉零残留 |
| 策略 | 策略 A(全便携)官方原生支持 |

**注意**:SQLite 在 U 盘上运行需安全弹出再拔,避免写库损坏。
