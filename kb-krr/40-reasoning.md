# 推理机制：本体如何"自动想出新事实"

## 一句话定位

**推理（Reasoning）= 利用 TBox/RBox 的规则，从 ABox 的已知事实里推导出未显式存储的新事实，并检查整个知识库是否自洽。** 背后跑的是 Tableau 算法一族；对外表现为四个标准任务：可满足性、分类、一致性、实例化。

---

## 一、四大推理任务（对外视角）

| 任务 | 问的是 | 输入 | 输出 | 例子 |
|---|---|---|---|---|
| **可满足性** | 某概念有没有可能非空？ | 概念表达式 + TBox | 是/否 | `Man ⊓ Woman` 可满足吗？→ 否 |
| **分类** | 类与类之间的完整包含关系？ | TBox（+RBox）| 分类树/格 | 把 1000 个类整理成层级 |
| **一致性** | KB 有没有内部矛盾？ | 整个 KB | 一致/不一致 | 个体既是 Man 又是 Woman？ |
| **实例化** | 某个体属于哪些（隐含）类？ | ABox + TBox/RBox | 新类型断言 | `Father(zhangsan)` 被推出 |

> 核心洞察（同 [[20-dl]]）：**四个任务全部规约到"概念可满足性判定"**。推理器本质上只做一件事——"这个断言有没有一套解释能成立"。

---

## 二、Tableau 算法（内部视角，怎么实现的）

Tableau（完形树）算法是主流推理器（HermiT/Pellet/FaCT++/ELK）的内核。思路：

1. **要判定** `C ⊑ D`？转为判定 `C ⊓ ¬D` **不可满足**（即"有没有解释"）。
2. 用**展开规则（expansion rules）**把概念表达式逐步拆开，构造一棵"完形树"（ABox 树），每个节点代表一个个体、节点间连角色边。
3. 反复套规则（交 → 拆成两个分支、存在 → 生成新个体、全称 → 检查邻居…），直到：
   - **不能再展开且无矛盾** → 存在解释 → 可满足；
   - **出现矛盾（如个体同时属于 C 和 ¬C）** → 无解释 → 不可满足。
4. 保证**终止**（有限的展开）和**完备**（找遍所有分支），这就是"可判定"的含义。

```
判定：Father ⊑ Person？
  转化为：Father ⊓ ¬Person 可满足吗？
    展开 Father → Man ⊓ ∃hasChild.Person
    → 节点 n 是 Man，且 n --hasChild--> 新节点 m，m 是 Person
    → 同时要求 n 是 ¬Person
    → 检查 TBox：Man ⊑ Person？是 ⇒ n 也是 Person ⇒ 矛盾！
  结论：Father ⊓ ¬Person 不可满足 ⇒ Father ⊑ Person 成立 ✅
```

---

## 三、分类（Classification）——最常用的推理

推理器把 TBox 里所有类两两算一遍包含关系，输出**完整的类层级**：

- 先饱和（saturate）TBox：把每个类拆成原子概念；
- 对每对类 (C, D) 判定 `C ⊑ D`；
- 优化技巧：**增量/分治**（只算"可能有关"的对）、**缓存已判定的传递闭包**，避免 O(n²) 全扫。

分类结果是本体"体检报告"：能发现隐藏的等价类、意外的子类、以及"幽灵概念"（不可满足的类）。

---

## 四、实例化（Materialization / Realization）

对 ABox 里每个个体，算出它**蕴含**属于的所有类（不仅显式写的）：

```
TBox:  Father ≡ Man ⊓ ∃hasChild.Person
ABox:  Man(zhangsan), hasChild(zhangsan,lisi), Person(lisi)
⇒ 推理：Father(zhangsan)   ← 自动补全
```

材料化（materialization）就是"把这些隐含事实显式写进数据"，之后 SPARQL 查询能直接命中，不用每次推理。**代价是推理时间换查询速度**——数据量大时是工程权衡点。

## 五、复杂度与"为什么 OWL 要分剖面"

| 逻辑 | 可满足性复杂度 | 代表推理器 |
|---|---|---|
| EL++（OWL 2 EL）| P（多项式）| ELK（百万级公理秒级）|
| DL-Lite（OWL 2 QL）| 查询重写后近线性 | Ontop（翻译成 SQL）|
| SROIQ（OWL 2 DL）| N2ExpTime | HermiT / Pellet / Konclude |
| OWL 2 RL | 线性（规则引擎）| Jena OWL RL / RDFox |

**工程含义**：选 [[22-profiles]] 就是选"复杂度档位"；表达力越强，最坏情况越慢。实际使用中，中小本体 DL 也是秒级，别被最坏复杂度吓到。

## 六、推理器是怎么被调用的（三种姿势）

| 姿势 | 方式 | 适合 |
|---|---|---|
| **图形界面** | Protege `Reasoner → HermiT → Start` | 建模时交互验证 |
| **Java API** | OWL API + HermiT/Pellet 库 | 开发语义应用 |
| **Python** | owlready2（内置 HermiT/Pellet）| 快速原型/脚本 |
| **规则引擎** | Jena OWL RL、RDFox | 大规模数据校验 |

## 七、常见误区

1. **以为推理是"魔法"**：推理只做**逻辑必然**的结论；语义没写清（少写了公理）就推不出，不是推理器笨。
2. **以为本体越强越好**：属性链、复杂角色会让复杂度飙升（NLogTime→N2ExpTime），"够用"优先。
3. **忽视一致性**：推理器报不一致不是 bug，而是你建模有矛盾——先修本体，别关掉推理。
4. **材料化与查询混为一谈**：要不要 materialize，取决于"数据多大、查询多频"，是典型工程取舍。

---

## 记忆口诀

- **四任务**：可满足、分类、一致、实例化——**都归约为"有没有解释"**；
- **Tableau 三招**：展开（拆式子）、分支（找解释）、判矛盾；
- **分类是体检**：跑一遍 = 发现等价、意外子类、幽灵概念；
- **实例化是补全**：把"该有的类型"显式写进数据。

一句话总结：**推理 = 用 TBox/RBox 的规则对 ABox 做逻辑必然的补全与校验；Tableau 算法是内核、四个任务是接口、复杂度是选型依据——理解这三层，你就能读懂任何推理器的行为。**
