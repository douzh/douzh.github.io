# Trilium Notes vs Protege：做"有链接属性的笔记"的对比

先说一个关键前提，避免选错：**两者虽然都"用链接连接笔记/实体"，但"链接"是完全不同性质的东西**——Trilium 的链接是**服务于笔记工作流的轻量关系**，Protege 的链接是**服务于语义推理的形式化公理**。下面详细拆。

---

## 一、本质定位

| | **Trilium Notes** | **Protege** |
|---|---|---|
| 定位 | 分层笔记应用，目标就是"构建大型个人知识库" | 本体建模/编辑工具，面向知识工程 |
| 核心问题 | "帮我记、组织、关联、查到想法" | "帮我严格定义概念与关系，并让机器推理" |
| 用户 | 个人知识管理（含开发者） | 本体工程师、研究员 |
| 维护现状 | 原版 2024-01 进入维护模式，社区 fork **TriliumNext** 活跃开发中 | 斯坦福维护，5.6.x 活跃更新 |

**关键事实**：原 Trilium 开发者 Zadam 已于 2024 年 1 月把项目移交社区，**TriliumNext** fork 继续开发（GitHub 上活跃，含中文界面、服务器版、Docker）。所以现在装要装 **TriliumNext**，别装已停更的原版。

---

## 二、"链接"的底层机制对比（核心差异）

| | **Trilium（关系属性 Relation）** | **Protege（对象属性断言）** |
|---|---|---|
| 什么是链接 | 笔记间的有向"关系"，如 `A ~references B`、`A ~包含 B` | 个体间的对象属性断言，如 `hasReference(A,B)` |
| 是否自动反向 | ✅ 建 `A references B` 自动生成 `B referencedBy A` | ❌ 需手动维护或靠逆角色公理推导 |
| 有无类型约束 | 弱——关系名随意，不校验指向的笔记类型 | 强——可声明 domain/range、子属性、不相交 |
| 可继承 | ✅ 标签/关系沿笔记树**向下继承** | ❌（公理全局作用） |
| 能否推理 | ❌ 无逻辑推理，只是"记录+查询" | ✅ 完整推理（传递、对称、逆、属性链） |
| 查询方式 | 属性搜索、保存的查询（saved search） | DL Query / SPARQL |
| 存储形态 | 本地库（SQLite）+ 可选自托管同步 | 本体文件（.owl/.ttl）+ 可接推理器 |

一句话：**Trilium 的链接 ≈ 手工维护的"ABox 断言 + 查询"；Protege 的链接 ≈ 带公理的"TBox+RBox+ABox"，且能自动推导。** Trilium 缺的正是 Protege 最强的部分——语义与推理；Protege 缺的则是 Trilium 的全部优势——笔记录入体验。

---

## 三、逐维度详细对比

| 维度 | Trilium（TriliumNext） | Protege | 胜者（看场景） |
|---|---|---|---|
| **录入体验** | 富文本/Markdown 双模式、代码块、公式、表格，随手记 | 表单式逐条填类/属性/个体，极其繁琐 | Trilium（差距巨大） |
| **组织方式** | 无限层级树 + **克隆**（一条笔记可同时挂多个位置）+ 双链 | 类层级树 + 个体归类 | Trilium |
| **全文检索** | ✅ 全文搜索 + 属性过滤 + 保存查询 | ❌ 无全文检索，只能结构化查询 | Trilium |
| **图谱视图** | ✅ 内置知识关系图谱（可视化关系网络） | ✅ OntoGraf 插件可画，但为调试而设 | 平手 |
| **自动推理** | ❌ 无 | ✅ HermiT/Pellet/ELK/Konclude | Protege（唯一强项） |
| **脚本/扩展** | ✅ 内置 JavaScript 脚本 + API，可编程的知识库 | ✅ 插件体系 + OWL API | 平手（方向不同） |
| **移动端** | ✅ Android（TriliumDroid 非官方 app）+ PWA | ❌ 无 | Trilium |
| **部署形态** | 桌面单机 / 服务器自托管 / Docker / 云 | 桌面 / WebProtégé（服务器） | Trilium（更灵活） |
| **加密** | ✅ 笔记级端到端加密 | ❌ | Trilium |
| **许可** | AGPL-3.0（开源） | BSD-2（开源） | 平手 |
| **学习成本** | 低（属性系统需适应，但一周上手） | 高（需懂 DL/OWL） | Trilium |

## 四、结论：怎么选

### 场景 1：你的核心需求是"笔记"（默认）
**选 Trilium（TriliumNext）。** 理由：
- "有链接属性的笔记"正是它的设计初衷——树 + 克隆 + 标签 + 关系 + 图谱 + 全文搜索，一套全内置；
- 你之前研究过 Zettelkasten，Trilium 的属性网络（label/relation + 继承 + 保存查询）比 Obsidian 更接近"可编程 PKM"；
- Windows 桌面端、可离线、可自托管，数据完全在你手里。

### 场景 2：你要的是"语义建模 + 推理"（比如规范引用自动推导）
**选 Protege（+ 推理器）。** 但要接受：它不是笔记工具，录入和查询体验对"记笔记"来说是灾难。

### 场景 3（推荐给你）：两者组合，Trilium 当"前端笔记库"，本体当"语义增强层"
```
日常记录/关联 → Trilium（低摩擦，属性网络管理关系）
                  ↓ 用脚本/API 定期导出 RDF/OWL
语义索引与推理 → Protege 建模 + Jena Fuseki 存储
                  ↓
                  SPARQL 做跨笔记推理查询（如规范 A→B→C 传递链）
```

**判断一句话**：如果你在意"**能不能推理出我没想到的关系**"→ Protege；如果你在意"**能不能舒服地记、查、关联，且长期用得住**"→ Trilium。对个人笔记知识库，**99% 的场景 Trilium 是正解**，Protege 只在你确有"自动推导"刚需时才值得引入。
