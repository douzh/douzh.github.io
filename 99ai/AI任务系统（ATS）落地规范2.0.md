# AI任务系统（ATS）落地规范2.0

——五层架构 + 全流程文档同步闭环落地版

## 前言

本规范是在**AI任务系统（ATS）原始五层架构落地规范**的核心逻辑基础上，深度融合**全链路软件工程文档同步产出、多AI协作场景适配、纯文件化存储与中断恢复**三大核心能力，升级形成的2.0版本。

规范明确了ATS五层架构（Vision→Problems→Goals→Tasks→Plans）与**需求文档（BRD/FRD）、产品设计文档（PDD）、架构文档（AD）、设计文档（HLD）、详细设计文档（DD）、开发计划（DP）**六类核心文档的**逐层级映射关系、同步产出规则、执行闭环逻辑**，同时定义了动态调整、版本管理、多AI协作的全流程标准，适用于AI驱动的软件项目、AI Agent开发、企业级AI应用落地等全场景。

# 一、核心升级与2.0定位

## 1.1 2.0版本核心升级点

|**升级维度**|**1.0版本（基础版）**|**2.0版本（落地闭环版）**|
|---|---|---|
|文档体系|无文档关联，仅任务拆分|新增6类软件工程文档，**逐层级同步产出**，与任务拆分强绑定|
|关联逻辑|五层架构独立运行|五层输出物 = 对应文档章节内容，**树状关联、可汇总、可追溯**|
|执行闭环|仅任务执行，文档滞后|执行过程同步更新文档，**执行进度=文档状态**，形成闭环|
|协作适配|单AI/人工协作|支持多AI交替/并行协作，**文档为核心协作载体**|
|容错恢复|仅任务进度记录|全文档版本回溯，**中断恢复时读取文档即可还原现场**|
|交付物|仅任务执行结果|全链路文档+执行结果双交付，配套**操作手册**|
## 1.2 2.0版本核心目标

- 1.  **任务拆分与文档产出并行**：每一层级的拆分动作，同步生成对应文档章节，杜绝文档遗漏、与执行脱节。

- 2.  **全链路可追溯**：任意层级的修改/执行，均可通过文档快速追溯关联关系，实现“改一处、全联动”。

- 3.  **纯文件化存储**：所有内容以Markdown格式存储，无数据库依赖，支持本地/云端文件系统部署，适配多AI快速接手。

- 4.  **执行与文档一致**：任务执行过程中，同步更新文档状态，确保“文档永远是最新执行记录”。

- 5.  **快速落地复用**：提供标准化目录结构、文档模板、流程指引，降低AI团队落地成本。

# 三、ATS五层架构 + 文档同步逐层级规范

## 3.1 第一层：Vision（愿景层）—— 顶层文档锚点

### 3.1.1 核心定义

愿景是项目的**长期价值方向**，不涉及具体功能、技术细节，仅明确“要成为什么、创造什么价值、最终交付什么”。

### 3.1.2 拆分与文档同步流程

1. **引导用户创建愿景**

    - 系统输出引导语，明确愿景需包含的核心要素：
                请描述你的AI项目愿景，需包含：① 核心价值（解决什么问题、创造什么价值）；② 目标场景/用户群体；③ 长期状态；④ 最终交付物边界。
              

    - 用户提交初步愿景描述。

2. **愿景确认与校准（同步写入愿景文档章节）**向用户展示确认内容，示例：
          我对您的愿景理解如下，请确认：

          ✅ 愿景描述：[标准化内容]

          ✅ 最终交付物：[清单形式]

          对应文档：
          - 需求文档：/reqs/brd_vision.md#1-愿景需求章节
          - 产品文档：/prod/pdd_vision.md#1-愿景产品章节
          - 架构文档：/arch/ad_vision.md#1-愿景架构章节
        

    - 系统提炼核心要素，生成**标准化愿景描述**，同步写入以下文档章节：
              

    - /reqs/brd_vision.md → **1. 愿景需求章节**

    - /prod/pdd_vision.md → **1. 愿景产品章节**

    - /arch/ad_vision.md → **1. 愿景架构章节**

### 3.1.3 终止条件

用户确认愿景描述、最终交付物与文档章节内容准确无误。

### 3.1.4 文档章节关联规则

|**文档章节**|**核心填充内容**|**上级关联**|**下级关联**|**交付物闭环**|
|---|---|---|---|---|
|愿景需求章节|愿景描述、核心价值、目标场景、最终交付物（与ATS愿景一致）|无|关联「问题需求章节」（问题需围绕愿景拆解）|愿景最终交付物 = 本章节核心内容|
|愿景产品章节|产品长期定位、核心价值方向、目标用户群体、产品形态预期|无|关联「问题产品章节」（产品问题需匹配此定位）|产品长期定位 = 本章节内容|
|愿景架构章节|长期架构方向、技术栈预期、系统规模、部署形态预期|无|关联「问题架构章节」（架构问题需对齐此方向）|架构长期预期 = 本章节内容|
## 3.2 第二层：Problems（问题层）—— 需求/产品/架构问题锚点

### 3.2.1 核心定义

问题是**现状与愿景的差距**，从需求、产品、架构三个维度拆解，明确“为什么要做、阻碍是什么”。

### 3.2.2 拆分与文档同步流程

1. **解析愿景相关核心问题**同步写入以下文档章节：

    - 系统基于确认后的愿景，从三个维度拆解问题：
              

    - 需求维度：业务缺口、用户痛点、需求未满足点；

    - 产品维度：功能缺失、交互缺陷、体验短板；

    - 架构维度：技术栈不匹配、模块耦合、性能瓶颈、架构短板。

2. /reqs/brd_problems.md → **2. 问题需求章节**

3. /prod/pdd_problems.md → **2. 问题产品章节**

4. /arch/ad_problems.md → **2. 问题架构章节**

5. **问题清单确认**

    - 向用户展示问题清单及对应文档章节链接，示例：
                基于您的愿景，拆解出以下核心问题，请确认是否补充/调整：
    
                1. 需求问题：[描述] → 对应文档：reqs/brd_problems.md#2-1-需求问题
                2. 产品问题：[描述] → 对应文档：/prod/pdd_problems.md#2-1-产品问题
                3. 架构问题：[描述] → 对应文档：arch/ad_problems.md#2-1-架构问题
              

### 3.2.3 终止条件

用户确认问题清单全面、准确，锁定对应文档章节。

### 3.2.4 文档章节关联规则

|**文档章节**|**核心填充内容**|**上级关联**|**下级关联**|**交付物闭环**|
|---|---|---|---|---|
|问题需求章节|现状与愿景的差距、用户痛点、业务缺口（逐条对应ATS问题清单）|关联「愿景需求章节」|关联「目标需求章节」（每个问题转化为1个目标需求）|问题清单 = 本章节所有问题条目|
|问题产品章节|产品当前痛点、功能缺失、交互问题、体验差距（对应ATS问题）|关联「愿景产品章节」|关联「目标产品章节」（每个产品问题转化为1个产品目标）|问题清单 = 本章节所有问题条目|
|问题架构章节|现有架构与愿景的适配性问题、技术栈短板、模块耦合、性能瓶颈（对应ATS问题）|关联「愿景架构章节」|关联「目标架构章节」（每个架构问题转化为1个架构目标）|问题清单 = 本章节所有问题条目|
## 3.3 第三层：Goals（目标层）—— 需求/产品/架构落地 + 设计/开发计划锚点

### 3.3.1 核心定义

目标是**将问题转化为可衡量、可验证的具体结果**，明确每个目标的交付范围、验收标准，同时承接设计与开发计划的顶层定义。

### 3.3.2 拆分与文档同步流程

1. **拆分目标与目标交付物**

    - 系统将每个问题拆解为符合**SMART原则**的目标，同步写入以下文档章节：
    

    - /reqs/brd_goals.md → **3. 目标需求章节**

    - /prod/pdd_goals.md → **3. 目标产品章节**

    - /arch/ad_goals.md → **3. 目标架构章节**

    - /design/hld_goals.md → **1. 目标设计章节**（概要设计）

    - /plan/dp_goals.md → **1. 目标开发计划章节**（目标级排期、里程碑）

2. **目标清单确认**

    - 向用户展示目标清单、对应交付物及文档章节链接，示例：
                基于问题清单，拆分出以下目标，请确认：
    
                目标1：[名称]，衡量指标：[具体指标]，交付物：[清单]
                对应文档：
                - 需求：reqs/brd_goals.md#3-1-目标1需求
                - 产品：prod/pdd_goals.md#3-1-目标1产品
                - 架构：arch/ad_goals.md#3-1-目标1架构
                - 设计：design/hld_goals.md#1-1-目标1设计
                - 计划：plan/dp_goals.md#1-1-目标1计划
              

### 3.3.3 终止条件

用户确认目标清单全面、匹配问题需求，锁定对应文档章节。

### 3.3.4 文档章节关联规则

|**文档章节**|**核心填充内容**|**上级关联**|**下级关联**|**交付物闭环**|
|---|---|---|---|---|
|目标需求章节|每个目标的SMART描述、需求范围、验收标准（对应ATS目标）|关联「问题需求章节」|关联「任务需求章节」（每个目标拆解为多个任务需求）|目标交付物 = 本章节核心内容（可汇总为愿景交付物）|
|目标产品章节|每个目标对应的产品功能规划、流程设计、交互原型方向（对应ATS目标）|关联「问题产品章节」|关联「任务产品章节」（每个产品目标拆解为多个任务产品）|目标交付物 = 本章节核心内容（可汇总为愿景交付物）|
|目标架构章节|每个目标对应的架构调整、模块新增/优化、技术选型落地（对应ATS目标）|关联「问题架构章节」|关联「任务架构章节」（每个架构目标拆解为多个任务架构）|目标交付物 = 本章节核心内容（可汇总为愿景交付物）|
|目标设计章节|目标对应的模块概要设计、接口定义、数据库概要设计（基于目标架构）|关联「目标架构章节」|关联「任务设计章节」（每个目标设计拆解为多个任务设计）|目标设计交付物 = 本章节核心内容|
|目标开发计划章节|目标级迭代周期、关键里程碑、依赖资源、交付时间（对应ATS目标）|关联「目标需求/产品/架构章节」|关联「任务开发计划章节」（每个目标计划拆解为多个任务计划）|目标计划交付物 = 本章节核心内容|
## 3.4 第四层：Tasks（任务层）—— 设计/详细设计/开发计划锚点

### 3.4.1 核心定义

任务是**将目标拆解为可独立执行、可明确责任的具体工作**，是连接目标与计划的核心，同时承接详细设计与任务级开发计划。任务需具备独立性，避免交叉冗余，可分配给单个AI/开发人员执行，其交付物需可验证，与目标交付物形成“下级汇总为上级”的树状关联。

### 3.4.2 拆分与文档同步流程

1. **拆分任务与任务交付物**

    - 系统结合AI开发流程（数据→模型→架构→开发→测试→部署），将每个目标拆解为具体任务，同步写入：
             

    - /design/hld_tasks.md → **2. 任务设计章节**

    - /detail/dd_tasks.md → **1. 任务详细设计章节**

    - /plan/dp_tasks.md → **2. 任务开发计划章节**

2. **任务清单确认**

    - 示例展示：
                任务1：[名称]，核心职责：[内容]，交付物：[清单]
                对应文档：
                - 设计：design/hld_tasks.md#2-1-任务1设计
                - 详细设计：detail/dd_tasks.md#1-1-任务1详细设计
                - 计划：plan/dp_tasks.md#2-1-任务1计划
                关联目标：[目标名称]
              

### 3.4.3 终止条件

用户确认任务清单全面、覆盖目标交付范围，任务职责与交付物清晰，锁定对应文档章节。

### 3.4.4 文档章节关联规则

|**文档章节**|**核心填充内容**|**上级关联**|**下级关联**|**交付物闭环**|
|---|---|---|---|---|
|任务设计章节|模块设计、核心流程、接口定义、数据库设计|关联「目标设计章节」|关联「计划设计章节」|任务设计交付物 = 本章节内容|
|任务详细设计章节|类结构、函数/方法、字段、状态机、异常处理|关联「任务设计章节」|关联「计划详细设计章节」|任务详细设计交付物 = 本章节内容|
|任务开发计划章节|任务级迭代、开发/测试/联调节点、责任人、依赖任务、交付时间|关联「目标开发计划章节」|关联「计划执行计划章节」|任务计划交付物 = 本章节内容|
## 3.5 第五层：Plans（计划层）—— 最终执行文档锚点

### 3.5.1 核心定义

计划是**将任务拆解为可落地、可按时完成的具体执行步骤**，是ATS落地的最终执行依据，也是文档同步的最后一环。计划层是纯文件化存储与中断恢复的核心载体，中断后可通过计划层文档快速还原执行进度。

### 3.5.2 拆分与文档同步流程

1. **拆分计划步骤与执行细节**

    - 同步写入：
              

    - /detail/dd_plans.md → **2. 计划详细设计章节**

    - /plan/dp_plans.md → **3. 计划执行计划章节**

2. **计划清单确认**

    - 示例展示：
                计划步骤1：[名称]，执行动作：[操作]，时间：[时间]，责任人：[AI/人员]，输出物：[内容]
                对应文档：
                - 详细设计：detail/dd_plans.md#2-1-计划步骤1详细设计
                - 执行计划：plan/dp_plans.md#3-1-计划步骤1执行计划
                关联任务：[任务名称]
              

3. **计划执行与文档同步更新**

    - 每完成一步，更新文档状态：`已完成 / 进行中 / 待执行`

    - 中断时记录：中断时间、当前进度、待执行步骤

    - 多AI协作以**计划文档**为唯一协作载体

### 3.5.3 终止条件

所有计划步骤执行完成，文档状态全部为「已完成」，交付物符合验收标准，用户确认闭环。

### 3.5.4 文档章节关联规则

|**文档章节**|**核心填充内容**|**上级关联**|**下级关联**|**交付物闭环**|
|---|---|---|---|---|
|计划详细设计章节|每一步技术细节、代码片段、异常处理|关联「任务详细设计章节」|无|计划详细设计交付物 = 本章节内容|
|计划执行计划章节|执行动作、时间、责任人、输出物、验收标准、依赖步骤|关联「任务开发计划章节」|无|计划执行交付物 = 本章节内容|
# 四、动态调整与版本管理规范

## 4.1 调整触发条件

- 愿景变更

- 问题新增/删除

- 目标调整

- 任务拆分不合理

- 计划延期或需求变更

## 4.2 调整流程

1. 提出调整申请（描述调整内容、原因、影响范围）

2. 评估影响层级（Vision/Problems/Goals/Tasks/Plans）

3. 修改对应文档章节

4. 同步更新关联文档

5. 生成新版本并归档历史

6. 用户确认

## 4.3 版本命名规则

`V主版本.次版本.修订号`

- 主版本：架构/流程重大变更

- 次版本：文档/任务结构调整

- 修订号：文案、细节修正

示例：`V2.0.1`

## 4.4 历史归档

所有历史版本存入各文档目录下 `/history/`，命名：

`[文档名]_Vx.y.z_日期.md`

# 五、多AI协作规范

## 5.1 协作模式

- 主AI：统筹五层拆分、文档生成

- 执行AI：按计划执行任务、回填文档

- 审核AI：校验交付物、验收标准

## 5.2 协作载体

**唯一协作载体：Markdown文档**

- 不使用即时消息、任务平台

- 所有状态、进度、结果只写进文档

## 5.3 交接规则

1. 读取当前文档状态

2. 确认已完成/待执行步骤

3. 继续执行并更新文档

4. 完成后标注完成时间与结果

# 六、中断恢复与故障容错规范

## 6.1 中断场景

- AI切换

- 会话断开

- 系统重启

- 人工暂停

## 6.2 恢复流程

1. 读取 `/ats/ats_task_management.md` 定位当前层级

2. 加载对应文档：BRD/PDD/AD/HLD/DD/DP

3. 恢复任务状态、计划进度

4. 继续执行，不重复、不遗漏

## 6.3 纯文件化恢复优势

- 无数据库依赖

- 可本地/云端存储

- 可Git管理

- 可跨设备、跨AI迁移
